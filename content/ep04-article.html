Does fine-tuning still have a place?

Every AIOps design review lately is about retrieval. Plain RAG, hybrid RAG, graph RAG, agentic RAG. Fine-tuning barely comes up, and when it does the answer is usually "the frontier model already does that." It's starting to feel like fine-tuning has no seat at the table in an autonomous operations flow.

The literature says otherwise. Predibase fine-tuned small models that beat GPT-4 on narrow tasks for under $8 each. RAFT trains models specifically to read retrieved documents. DoorDash built its support stack on retrieval precisely because the knowledge base changes daily. None of that is "pick one."

This isn't research. It's an afternoon of code to see, on an ops task I understand, where the boundary sits for an agent that has to act without a human checking its work.

The rule under test

RAG changes what the model sees at answer time; fine-tuning changes how it behaves. Reach for RAG when the knowledge moves. Reach for fine-tuning when behavior is the problem. The strongest systems do both. Paolo Perrone, RAG vs Fine-Tuning — When to Use Each in Production, The AI Engineer, July 2026

Clean rule. Easy to nod at. The question is whether it survives contact with a real task, and what it costs when you get the split wrong.

The task — an autonomous triage agent, built both ways

A fictional shop, NimbusCart. Six services, each with an owning team, an escalation channel, a runbook id and one known failure mode. This is the first hop of an AIOps pipeline: an alert fires, and a triage agent, not a person, decides severity, names the service and probable cause, picks the runbook, and routes the incident to a team channel. Its output is one JSON object downstream automation acts on. No human reads it first.

The point of this task is that you could build the agent either way. Put the runbooks and service catalog in a retrieval index and hand the model the right page at inference. Or write 360 example triages and fine-tune the operating policy in. Both feel reasonable. Both would demo well. So I built both, plus neither, plus both together, and scored all four on the same 24 alerts.

{"severity":"P1","affected_service":"checkout-svc",
 "probable_cause":"db connection-pool exhaustion during flash sales",
 "runbook_ref":"RB-CHK-001","escalate_to":"#atlas-oncall","escalate":true}

Scoring is deterministic, no LLM judge. JSON: exactly one valid object, six keys. Severity: matches the org's P1/P2/P3 policy. Facts: runbook id, routing channel and service match the service catalog. Retrieval is TF-IDF over 8 markdown docs, deliberately boring. LoRA is rank 8 on the last 16 of 32 layers, 600 iterations; loss hit 0.000 at iteration 70.

Day one only. Retrieval (① → ②) lifts teal and leaves amber flat: docs carry facts, not judgement. The adapter (① → ③) lifts amber: the escalation policy is learned. And ③ is tallest on everything, which is exactly why teams ship it.

Read that on its own and the conclusion writes itself: fine-tune wins, retrieval is a tax. Every number in ③ is real. It is also the trap, because the 24 eval alerts are the same 24 templates the adapter trained on, with new values. ③'s facts are a memorised answer key from the day the training data was written.

Which raises the only question that matters: what happens the day after?

Day two — the reorg

NimbusCart dissolves team-atlas. checkout-svc now belongs to team-borealis, routing channel #borealis-oncall. Someone updates the service catalog. Nobody retrains anything, because nobody thinks of the triage agent as something that needs retraining when a team moves. Same four checkout alerts, same three configs that could possibly know:

The fine-tuned agent routes every checkout incident to a team that no longer exists. Four times out of four. Perfect JSON, full confidence, no error, and no human in the loop to catch it.

"So why not just retrain?"

Fair question, and the one this experiment exists to answer. You can retrain. Here is what that costs for an agent in production versus updating the catalog, and why the boundary isn't about effort.

when a fact changesupdate the catalog (RAG)retrain (fine-tune)
what you touchone line in the service catalogregenerate the training set (every example that mentions the old fact: 62 of 360 here), rerun training, re-evaluate, redeploy
time to correct answersthe next request~40 min compute for 600 iterations on this Mac, plus data prep and eval. Wall clock was 10 h because the Mac slept.
who can do itwhoever owns the service, as part of the reorg itselfwhoever owns the agent's training pipeline, who wasn't in the reorg meeting
how you find out it's staleyou don't need to; the catalog is the truthyou don't. ③ scored 100% on its own eval the day it went stale, and an autonomous agent has no operator watching each decision.
how often this happensowners, channels, thresholds, runbook steps, dependency maps: weekly in a real platform org. Every change is a retrain, forever, one run behind reality.
what fine-tuning is forthe agent's operating policy, which doesn't change per incident: the severity rule, the output contract downstream automation parses, the tone of the incident record. The adapter learned those once and kept them through the reorg.

So the boundary: if it lives in a system of record, it's retrieval. If it's how the agent is supposed to behave, it's fine-tuning. Owners, channels, rotations, thresholds, runbook steps, dependency graphs go in the index, where the CMDB and the runbook repo already are. "P1 means a paying customer is blocked, and the record has six fields, no prose" goes in the weights. An autonomous agent needs both, and ④ is the only cell that was right on both days.

What each lever actually bought

retrieval bought
  • Runbook id 0% → 88%, channel 0% → 88%, from three chunks in the prompt.
  • Severity 71% → 75%. Judgement stayed where it was.
  • A catalog change that reached the agent when the file was saved.
the adapter bought
  • Severity 71% → 100%. The org's escalation policy the base model was guessing at.
  • Output contract: one line, the canonical phrase for the cause, a third of the tokens for the downstream parser.
  • Facts frozen on training day. 100% on v1, 0/4 after the reorg.

The map

If it lives in a system of record, retrieve it. If it's how the agent behaves, train it. Get either one backwards and you get the red boxes: a confident stale router, or a guessing one.

What I'd say against myself

  • "Format rescue" never showed. I expected the base to fumble JSON. Qwen3.5-4B with thinking off was 100% compliant. The behaviour gain here is the severity rule and the output contract, not syntax.
  • The severity gap is inflated. Eval values are template-agnostic, so some alerts read as nonsense ("5xx rate 9202%", "[INFO] pool utilisation 9404%"). Part of the base's misses is it reading the number where the adapter learned to trust the [FIRING]/[WARNING]/[INFO] tag. The claim stands; a cleaner run would show a smaller gap.
  • ④'s runbook misses are my bug, not the model's. All five (3 in ②, 2 in ④) are the model copying runbook-checkout-svc.md from the [doc › heading] label the retriever prefixes to each chunk. One-line fix for a follow-up.
  • "Held-out" is in-distribution. Same 24 templates, new region and values. ③'s day-one 100% is template recall.
  • Trained 9× longer than needed and the Mac slept twice. Compute ~40 min, wall clock ~10 h. caffeinate -i next time.
  • Scope. One model, one seed, one LoRA config, TF-IDF over 8 docs, 24 alerts, a fully synthetic org. These numbers describe this task, not "AIOps in general".

Fine print

Framework under test: Paolo Perrone, RAG vs Fine-Tuning — When to Use Each in Production. Model: mlx-community/Qwen3.5-4B-4bit via mlx-lm 0.31.3 on a 14" M5 Max, 128 GB. LoRA: rank 8, scale 20, last 16 of 32 layers, batch 4, 600 iterations, lr 1e-5, prompt-masked; 0.193% of parameters trained; adapter 31 MB. Data: 360 train / 40 valid / 24 eval, generated from 24 alert templates over 6 fictional services; eval uses an unseen region and value range. Retrieval: TF-IDF cosine, top-3 chunks by markdown heading over 8 docs. Scoring: deterministic, no LLM judge. Every output, score and the training log are in the repo: github.com/Suryals/mlx-lab, Episode 04, five commands to reproduce.
