# MLX Lab Ep 04 — RAG vs Fine-Tuning, tested on a synthetic on-call desk

**Date:** 2026-09-14 · **Mode:** shipping · **Status:** approved design, pending implementation plan

## Goal

Reproduce, in code and on one Mac, the rule from Paolo Perrone's *RAG vs Fine-Tuning*
(https://theaiengineer.substack.com/p/rag-vs-fine-tuning): **RAG changes what the model sees
(use it when knowledge moves); fine-tuning changes how the model behaves (use it when format,
tone, or skill is wrong); production usually wants both.** The article is credited explicitly
as the framework under test.

The experiment must show two things:
1. Each lever moves exactly one axis of the score (retrieval → fact accuracy, LoRA → behavior compliance).
2. A fact change after training breaks the fine-tuned-only model but not the retrieval-backed configs.

## Hard constraints

- **Fully synthetic domain.** Fictional company "NimbusCart". No service names, alert formats,
  runbooks, or team structures resembling any real employer's stack. Real-work AIOps and
  expense-policy domains were considered and rejected for this reason.
- Runs entirely locally on the M5 Max (128GB) with mlx-lm 0.31.x. No cloud training.
- Follows the existing repo layout: code in `bench/`, results in `results/`, write-ups in `content/`.

## The synthetic world

Six microservices with owner, escalation channel, runbook id, and one known failure mode each.
This table is the **ground truth** the scorer checks against.

| Service | Owner (v1) | Escalation (v1) | Runbook | Known failure mode |
|---|---|---|---|---|
| checkout-svc | team-atlas | #atlas-oncall | RB-CHK-001 | DB connection-pool exhaustion during flash sales |
| payments-gw | team-ledger | #ledger-oncall | RB-PAY-001 | Upstream PSP timeout → retry storm |
| inventory-svc | team-stockroom | #stockroom-oncall | RB-INV-001 | Cache/DB drift after bulk import |
| search-svc | team-lens | #lens-oncall | RB-SRCH-001 | Index rebuild starves query latency |
| notify-svc | team-beacon | #beacon-oncall | RB-NTF-001 | Queue backlog when email vendor rate-limits |
| auth-svc | team-gatekeeper | #gate-oncall | RB-AUTH-001 | Token-signing key rotation missed |

**Knowledge docs (v1):** ~12 markdown files in `data/ep04/docs_v1/` — service catalog,
ownership/escalation map, one runbook per service (symptoms, probable causes, remediation steps).

**Knowledge docs (v2):** identical copy in `data/ep04/docs_v2/` with one change — the reorg
(see Twist).

## Target output schema

```json
{
  "severity": "P1 | P2 | P3",
  "affected_service": "checkout-svc",
  "probable_cause": "connection pool exhausted under burst traffic",
  "runbook_ref": "RB-CHK-001",
  "escalate_to": "#atlas-oncall",
  "escalate": true
}
```

Format fields (valid JSON, all keys present, severity enum, no prose wrapper) are what LoRA should
fix. Fact fields (`affected_service`, `runbook_ref`, `escalate_to`) are what retrieval should fix.
`probable_cause` is free text and is not scored.

## Lever 1 — RAG (knowledge)

- Chunk docs by markdown heading; embed with a local sentence-embedding model; cosine top-3 into
  the system prompt under a "Reference material" header.
- Deliberately simple: no hybrid search, no reranker. Retrieval quality is not the story;
  editability is.
- Swapping `docs_v1` → `docs_v2` and re-indexing must take seconds.

## Lever 2 — LoRA fine-tune (behavior)

- Base: `mlx-community/Qwen3.5-4B-4bit` (dense 4B, Apache 2.0, `qwen3_5` loader in mlx-lm).
  Chosen over Llama-3.2-3B (two years old) and Gemma 4 E4B (heavier checkpoint, less-trodden
  loader, base already good at JSON which would mute the fine-tune axis). Gemma 4 E4B is a
  stretch goal: rerun the grid on it if time remains.
- Training data: ~400 chat-format JSONL pairs, alert text → triage JSON in a calm SRE voice,
  generated by `bench/ep04_gen_data.py` from templates (6 services × failure modes × varied
  metrics/regions/severities). v1 facts are deliberately baked into the answers. Split 360/40
  train/valid. Chief reviews a sample before training.
- Run: `mlx_lm.lora --train --fine-tune-type lora --num-layers 16 --batch-size 4 --iters 600
  --learning-rate 1e-5 --steps-per-eval 50`, config stored in `bench/ep04_lora.yaml`.
  Adapter saved to `adapters/ep04-qwen3.5-4b/`. Cut iters to ~300 if validation loss rises.
- Thinking mode disabled (`enable_thinking=False`) for training and eval so reasoning traces
  never enter the JSON-compliance score.
- Sanity gate: 10 hand-picked alerts through base vs tuned; tuned must produce valid JSON on
  ≥9/10 before the full grid runs.

## The experiment — 2×2 grid

Same eval set (`data/ep04/eval.jsonl`, ~20 alerts covering all six services, none copied from
training) against four configurations:

| | no retrieval | + RAG (docs_v1) |
|---|---|---|
| base model | ① base | ② base + RAG |
| fine-tuned | ③ tuned | ④ tuned + RAG |

Expected: ① fails both axes; ② facts ✓ format ✗; ③ format ✓ facts only as good as the training
snapshot; ④ both ✓.

**Scores per config** (`bench/ep04_eval.py`, results to `results/ep04-grid.json`):

| Score | Measures | Check | Should respond to |
|---|---|---|---|
| Fact accuracy | `affected_service`, `runbook_ref`, `escalate_to` | exact match vs ground truth | RAG |
| Behavior compliance | parses as JSON, all keys, severity ∈ {P1,P2,P3}, no prose wrapper | programmatic | LoRA |
| Latency (secondary) | TTFT, tokens/s per config | wall clock | shows RAG's extra hop vs tuned model's speed |

## The twist — reorg after training

After the grid: team-atlas is dissolved, checkout-svc moves to team-borealis, escalation to
`#borealis-oncall`. Only `docs_v2` differs from `docs_v1`. No retraining. Re-run the checkout
alerts through ②, ③, ④ → `results/ep04-reorg.json`.

Expected: ② and ④ answer `#borealis-oncall`; ③ still answers `#atlas-oncall`.

Known risk: ④ may still echo the stale channel if the adapter overpowers the retrieved passage.
That is a finding, not a failure (it is what RAFT-style training addresses) and goes in the post.

anything touching real production systems.
