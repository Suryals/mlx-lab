# Ep 03.5 — Quantization Robustness: Q4 vs Q6 vs Q8

> Follow-up to Ep 03, prompted by a reader question ("why not at least 8-bit? there are marginal
> % left in the quantisation"). Same 24-task suite, same deterministic scorer, 2 runs per quant.
> Raw data: `results/ep03-qwen3.8-27b-{4bit,q6-gguf,8bit-mlx}*.json`.

## Setup

| Rung | Weights | Runtime / path | Size |
|------|---------|----------------|------|
| Q4 (baseline, Ep 03) | `mlx-community/Qwen3.8-27B-4bit` | MLX in-process | 16.1 GB |
| Q6 | `lmstudio-community/Qwen3.8-27B-GGUF` Q6_K | LM Studio local server (OpenAI-compatible) | 23.4 GB |
| Q8 | `mlx-community/Qwen3.8-27B-8bit` | MLX in-process | ~30 GB |

⚠️ **The Q6 rung changes two variables at once** — quantization *and* runtime (llama.cpp via LM
Studio, server-side default sampling, its own chat-template handling). Q4 vs Q8 is the clean
apples-to-apples pair (identical runtime, effectively greedy decoding). Treat Q6 numbers as
"Q6-GGUF-through-LM-Studio", not "6-bit" in isolation.

## Results

| | Q4 · MLX (baseline) | Q6_K · GGUF/LM Studio | Q8 · MLX |
|---|---|---|---|
| Easy tier (18 × 2) | **36/36** | **36/36** | **36/36** |
| Hard tier (6 × 2) | **10/12** | 8/12 | **10/12** |
| Failed tasks | H04 ×2 | H04 ×2, H01 ×1, H03 ×1 | H04 ×2 |
| Run-to-run variance | none | run1 3/6, run2 5/6 | none (identical runs) |
| Unnecessary tool calls | 18 | 19 | 28 |
| Avg seconds / task | ~47 | 66 | 72 |
| Decode tok/s | 17 | n/a (not instrumented via server) | 10.5 |
| Prefill tok/s | ~400 | n/a | 388 |
| TTFT (first turn) | 3.5s | n/a | 3.7s |
| Peak unified memory | 18.2 GB | ~24 GB (LM Studio-managed) | 31.7 GB |

## Findings

1. **8-bit bought zero correctness on this suite.** Q8 reproduced the Q4 result exactly — 46/48,
   same single failure (H04), and its two runs were identical task-for-task. The "marginal %
   left in the quantisation" did not materialize here. Cost of checking: +13.5 GB RAM, decode
   down 17 → 10.5 tok/s (−38%), avg task time 47s → 72s.

2. **The H04 restraint trap is now the most robust finding of the series.** It has failed at
   every quantization level (Q4/Q6/Q8), on two runtimes (MLX, llama.cpp), and on Claude Opus 4.6
   over the API — 10 out of 10 attempts across all configurations. Obedience-over-restraint is a
   property of how these models are trained, not an artifact of precision, runtime, or scale.

3. **The Q6 rung mostly demonstrated why the harness must own the request path.** Its one weak
   run (dropped the red-herring and contradiction tasks once each) came with run-to-run variance
   that the MLX rungs don't have — consistent with LM Studio's server applying its own default
   sampling rather than greedy decoding. We can't attribute that gap to 6-bit weights; we *can*
   attribute it to an uncontrolled serving layer. (Ep 03's limitations section called this
   exact confound; here it is, measured.)

4. **More precision, more wandering.** Q8 made 28 unnecessary tool calls vs Q4's 18 —
   deterministically (identical across both runs). Precision changed the model's exploration
   personality without changing its correctness.

## Verdict

For local agentic use of Qwen3.8-27B on Apple Silicon: **run the 4-bit.** On this suite it is
as correct as 8-bit, 1.6× faster, and fits in 60% of the memory. If you want a quality margin
for other workloads, 6-bit is a size/speed compromise — but serve it through a path you control
and pin the sampling, or you're benchmarking your server's defaults, not your weights.
